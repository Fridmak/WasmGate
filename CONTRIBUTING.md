# Contributing to WasmGate

WasmGate is a small but security-sensitive data/control plane. Contributions are
welcome. Please keep changes focused, explain the problem, and prove the behavior
with tests.

This file covers contribution policy. Build, test and tooling details live in
[`docs/en/development.md`](docs/en/development.md) and
[`docs/ru/development.md`](docs/ru/development.md).

## Before you start

- Search existing issues and pull requests before opening a new one.
- For anything non-trivial, open or confirm an issue first.
- State the problem, expected behavior, scope, non-goals, and acceptance criteria.
- One logical change per pull request. Do not mix unrelated refactors, formatting,
  data-plane Go, control-plane C#, plugin ABI, and documentation changes.
- Security-sensitive changes (authentication, certificates, enrollment tokens,
  release signing, admin API, sandbox limits) need an explicit threat model.
- If a fix needs a new mechanism, explain why the existing one is insufficient.
  Remove obsolete compensation code in the same pull request; do not layer a
  second fallback on top.

## Development setup

Requirements:

- Go toolchain pinned by `go.mod` (currently Go 1.27.4).
- .NET 10 SDK (`control-plane/global.json` pins 10.0.404).
- Rust with the `wasm32-unknown-unknown` target for reference plugins.
- `clang` and `zlib` only for Native AOT publishing.
- `protoc`, `protoc-gen-go`, `protoc-gen-go-grpc` only when the gRPC contract
  changes.

Quick checks:

```bash
# Data plane (Go)
gofmt -l .                         # must print nothing
go vet ./...
go test -count=1 ./...
go test -race -count=1 ./...       # Linux CI; Windows needs CGO/gcc
golangci-lint run                  # v2.15.0, config in .golangci.yml

# Configuration and plugin validation
go run ./cmd/wasmgate -config configs/wasmgate.yaml -validate

# Control plane (.NET)
cd control-plane
dotnet build WasmGate.Control.sln -c Release
dotnet test WasmGate.Control.sln -c Release --no-build --no-restore
dotnet format WasmGate.Control.sln --verify-no-changes --no-restore

# Reference plugins (Rust)
cd ../plugins/examples
cargo fmt --all -- --check
cargo test --locked -p wg-common
cargo build --locked --workspace --release --target wasm32-unknown-unknown
```

If you change the gRPC contract:

```bash
make proto
```

Commit the regenerated Go bindings. C# bindings are generated by the build.

Never commit secrets, private keys, enrollment tokens, real CA material, or
real certificates. Use generated temporary fixtures in tests.

## Tests

A test must prove behavior, not merely that a method was called.

- Cover the happy path, failure path, cancellation, retry, and relevant
  concurrency cases.
- Endpoint changes should exercise the real endpoint and the real repository.
- Security fixes should cover revoked, expired, unknown, already-revoked, and
  replaced certificates where applicable.
- Concurrency and lifecycle tests must be deterministic. Use channels,
  `TaskCompletionSource`, barriers or explicit synchronization; do not use
  arbitrary sleeps.
- If a test is flaky, do not hide it with reruns. Fix it or open a tracking issue
  and get maintainer agreement.
- Run new concurrency/security tests more than once before opening the pull
  request.

## Concurrency and lifecycle changes

Lifecycle bugs are not fixed by adding a second fallback. Define the invariant,
choose one serialization point, and test the interleavings.

- Write the invariant first. For example: at most one current session per agent;
  a closing or failed session must never become current again.
- Prefer one owner for lifecycle state. Registry membership should be changed by
  the service that owns the operation, under one serialization point.
- Failure-prone work must happen before a takeover or state transition whenever
  possible. If a new registration can fail after displacing an old session, fix
  the ordering rather than adding restore/rollback flags.
- Keep critical sections short. Do not hold a lock while doing network I/O,
  closing a gRPC stream, or writing audit events; capture references, release
  the lock, then close.
- Document lock order. Do not introduce lock cycles.
- Do not claim that a check is periodic, matching, or atomic unless the code
  actually is.
- If a limitation is accepted, write it in the documentation and open a
  follow-up issue. Do not leave it implicit.

## Pull requests

- Use a focused branch: `fix/...`, `feat/...`, `test/...`, `docs/...`.
- Use Conventional Commits, for example:
  - `fix(control-plane): ...`
  - `feat(plugin): ...`
  - `test(control-plane): ...`
  - `docs: ...`
- The pull request description should explain:
  - the problem and linked issue;
  - what changed and why;
  - behavior/API/compatibility impact;
  - tests run;
  - security and availability risks;
  - accepted limitations and follow-ups.
- Use `Fixes #...` only when every acceptance criterion is met. Otherwise use
  `Refs #...` and list the remaining work.
- Do not add unrelated formatting or refactoring. If you need a refactor to make
  a fix correct, remove the old mechanism in the same pull request and explain
  why the net result is simpler.
- Do not force-push during active review unless the reviewer asks for it; add
  commits and let the reviewer see the changes.

## Review and CI

- Reviewers should check invariants, failure modes, security boundaries, and
  test quality, not only style.
- A green rerun is not evidence that a flaky or fatal failure is fixed. Explain
  the failure, reproduce it, or link a tracking issue.
- Resolve review conversations only after the fix is pushed and tested.
- CI must be green on the current commit before merge.
- If a failure is unrelated and known, link the existing issue and get
  maintainer agreement instead of silently rerunning.

## Documentation

Every tracked document exists in both languages:

- `README.md` / `README.ru.md`
- `docs/en/...` / `docs/ru/...`

Update both in the same commit. Also update, when relevant:

- CLI flags and environment-variable tables;
- API endpoint and status-code tables;
- UI strings (`wwwroot/app.js`);
- known limitations and security trade-offs;
- migration/upgrade notes and examples.

Documentation must describe actual behavior. Do not describe a best-effort
audit as guaranteed, a message-driven check as periodic, or an any-session close
as matching a specific certificate unless that is what the code does.

## Security issues

Do not open a public issue for a vulnerability. Use the repository's private
vulnerability reporting mechanism if available, or contact the maintainers
privately. Give enough detail to reproduce the issue, but do not include real
production secrets or customer data.

## Definition of done

A pull request is ready when:

- [ ] the problem and scope are clear;
- [ ] the behavior/API change and its limitations are documented;
- [ ] the happy path and failure paths are tested;
- [ ] concurrency/security-sensitive behavior has deterministic tests;
- [ ] no unrelated changes are included;
- [ ] Go formatting, `go vet`, lint and tests pass;
- [ ] race tests pass on Linux when the change touches concurrent Go code;
- [ ] control-plane build, tests and `dotnet format --verify-no-changes` pass;
- [ ] Rust formatting/tests/build pass when plugins change;
- [ ] generated files and committed `.wasm` artifacts are up to date;
- [ ] EN/RU docs are updated;
- [ ] CI is green on the current commit;
- [ ] follow-up work is recorded as an issue.
