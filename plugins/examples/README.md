# Примеры WASM-плагинов и ограничения песочницы (`internal/plugin`)

В `plugins/examples/` лежат **восемь** готовых плагинов: от L4-фильтра до L7-маршрутизации,
разбора TLS ClientHello, RESP-политики, мутации тела HTTP и stateful-инспекции тела
по ABI v3 (`on_data_state`). Исходники собираются одним workspace (`plugins/examples/Cargo.toml`),
а скомпилированные `.wasm` уже закоммичены — Rust для запуска не нужен.

| Плагин | Что демонстрирует | Режим | Вердикты |
|--------|-------------------|-------|----------|
| `ipguard` | `on_accept`: L4 allow/deny до `dial` (аналог `allow`/`deny`/`geo`) | L4 | `0` allow, `≠0` deny |
| `http_guard` | `on_data_ex`: методы/пути, Basic auth, CL+TE-smuggling, маскировка `Server`/`X-Powered-By` | `stream` | `0` / `1` |
| `http_body_guard` | `on_data_state` (ABI v3): сборка разорванных HTTP-заголовков, контроль `Content-Length`, межчанковый поиск сигнатур в теле и счётчики между keep-alive запросами | `stream` | `0` / `1` |
| `path_router` | `route_pools` по `Host` и пути (аналог `map`/`location`) | `once` | `2..4` → пулы |
| `sni_guard` | SNI из ClientHello без терминации TLS (аналог `ssl_preread` + `map`) | `once` | `2..4` → пулы |
| `protocol_router` | определение TLS/HTTP/SSH/PostgreSQL/Redis по первым байтам | `once` | `2..6` → пулы |
| `redis_guard` | разбор RESP и inline-команд, ACL на `CONFIG`/`FLUSHALL`/`EVAL` | `stream` | `0` / `1` |
| `stream_guard` | сигнатуры атак в теле запроса + in-place маскировка JSON-секретов в ответе | `stream` | `0` / `1` |

Готовый конфиг со всеми листенерами: `configs/showcase.yaml`.

```bash
go run ./cmd/wasmgate -config configs/showcase.yaml -validate
```

Минимальный пример подключения (`ipguard`, **89 байт**):

```yaml
listeners:
  - name: edge
    addr: "127.0.0.1:8080"
    upstream_pool: web
    plugin:
      path: "plugins/examples/ipguard/ipguard.wasm"
      max_memory_pages: 16   # 16 * 64 KiB = 1 MiB потолок памяти на инстанс
      timeout: 0s            # 0s = без таймера (0 allocs/op); trusted plugin only
      data_mode: "once"      # "once" (по умолчанию) | "stream"
      route_pools: ["canary"] # on_data >= 2 → route_pools[ret-2]
```

## 1. Контракт ABI (Go Host ↔ WASM Guest)

Ядро передаёт метаданные соединения **через стек регистров (`uint64`)** с помощью
`wazero` `CallWithStack`, без выделения строк и без копирования в линейную память
WASM. Это даёт **0 B/op и 0 allocs/op** (Linux, AMD Ryzen 5 3550H:
`on_accept` ≈ **81 нс** в один поток и ≈ **25 нс** параллельно; `on_data` ≈ **76 нс**).

Модуль обязан экспортировать хотя бы одну из **трёх** функций со следующей
сигнатурой:

| Экспорт | Сигнатура WASM | Аргументы | Возврат |
|---------|----------------|-----------|---------|
| `on_accept` | `(i64, i64, i32) -> i32` | `ip_hi`, `ip_lo` (16-байтный канонический IP в big-endian; для IPv4 это `::ffff:a.b.c.d`), `port` (TCP-порт клиента) | `0` = `VerdictAllow`, любое ненулевое значение = `VerdictDeny` (сбросить до `dial`) |
| `on_data` | `(i32, i32) -> i32` | `ptr`, `len` — указатель и длина массива байт пакета в линейной памяти плагина. **`on_data_ptr() -> i32` обязателен**. Буфер — до `32 KiB`, плагин может модифицировать байты на месте | `0` = `VerdictAllow`, `1` = `VerdictDeny`, `>= 2` = `route_pools[ret-2]` (только `once`) |
| `on_data_ex` | `(i64, i32, i32, i32) -> i32` | `conn_id`, `dir` (0 = client→server, 1 = server→client), `ptr`, `len`. `conn_id` стабилен в пределах соединения: его можно писать в логи/метрики и передавать в `on_close_ex`. Гостевое состояние между чанками на него **не опирается** — инстансы берутся из пула, память у них разная (см. §2.3) | как `on_data` |
| `on_data_state` | `(i64, i32, i32, i32, i32, i32, i32) -> i64` | `conn_id`, `dir`, `state_ptr`, `state_len`, `state_cap` (4 KiB), `data_ptr`, `data_len`. **Обязательны `on_data_ptr() -> i32` и `on_state_ptr() -> i32`** (непересекающиеся буферы в памяти гостя). Хост хранит по 4 KiB состояния на каждое направление соединения в `sync.Pool` | младшие 32 бита = `verdict` (`i32`), старшие 32 бита = `new_state_len` (`0..=4096`) |
| `on_close` | `(i64, i64, i64, i64) -> ()` | `ip_hi`, `ip_lo`, `rx_bytes`, `tx_bytes` | пусто |
| `on_close_ex` | `(i64, i64, i64, i64, i64) -> ()` | `conn_id`, `ip_hi`, `ip_lo`, `rx_bytes`, `tx_bytes` | пусто |

`on_data_ex`/`on_close_ex` — **опциональное расширение**; старые `on_data`/`on_close` работают как раньше. Если экспортирован `on_data`/`on_data_ex`, обязателен `on_data_ptr`: хост больше не пишет по фиксированному смещению 32768 и не может перезаписать данные гостя.

Отрицательные verdict-значения и `INT32_MIN` трактуются как deny; allow — только `0`. Индекс маршрута вне диапазона `route_pools` — deny, а не «default pool».

Если сигнатура экспорта не совпадает или модуль не экспортирует ни один из
трёх хуков, загрузка конфигурации / `Reload` завершается ошибкой до смены
snapshot'а (fail-fast).

## 2. Жёсткие ограничения на плагины (чего плагин делать НЕ может)

Эти ограничения — осознанный компромисс ради безопасности и `0 allocs/op` на
горячем пути (важно явно проговаривать на защите ВКР):

1. **Полное отсутствие WASI и системных вызовов (Pure Sandbox).**
   Гостевому модулю **не** предоставляются файловая система, сетевые сокеты,
   переменные окружения, системные часы или генератор случайных чисел. Плагин —
   чистая детерминированная функция от переданных метаданных соединения.
   Попытка импортировать `wasi_snapshot_preview1` без зарегистрированных хост-функций
   приведёт к отказу компиляции модуля на этапе старта/reload.
2. **Жёсткий потолок линейной памяти (`max_memory_pages`).**
   По умолчанию каждый инстанс ограничен **16 страницами (16 × 64 KiB = 1 MiB)**.
   - Если `.wasm` модуль в секции `memory` запрашивает `min > max_memory_pages`,
     он отвергается при загрузке (`TestPluginMemoryLimitRejectsOversizedModule`).
   - Если плагин внутри вызывает `memory.grow` сверх лимита, инструкция возвращает `-1`
     (выделение памяти внутри гостя получает OOM, не затрагивая процесс Go).
3. **Пул переиспользуемых инстансов (Reactor-модель, а не Command-модель).**
   Инстансы хранятся в `sync.Pool` и вызываются многократно для разных соединений:
   - глобальные переменные внутри WASM **сохраняются** между вызовами одного
     инстанса, но **не синхронизированы** между разными инстансами в пуле;
   - плагин не должен полагаться на то, что его глобальная память сбрасывается
     на каждое соединение, и не должен хранить секреты одного соединения в
     глобальном буфере.
4. **Ограничение по времени исполнения (`timeout`) и выбраковка при сбое.**
   - При `timeout > 0` включается `WithCloseOnContextDone(true)`: если хук
     зависает в бесконечном цикле или падает в `unreachable` (panic/trap),
     вызов принудительно прерывается, соединение отклоняется (`VerdictDeny`),
     а испорченный инстанс **закрывается и уничтожается**, а не возвращается в пул.
   - При `timeout: 0s` (по умолчанию) таймер на каждый вызов не создаётся, что
     сохраняет **0 аллокаций на соединение**. Это ответственность оператора:
     зависший цикл без таймаута может остановить процесс; при загрузке такого
     плагина ядро пишет WARN. Для недоверенных плагинов задавайте `timeout` явно.
5. **Два режима L7-инспекции (`on_data` + `data_mode: "once" | "stream"`).**
   - Если плагин **не** экспортирует `on_data`, прокси идёт по чистому L4 fast path (`splice(2)` на Linux).
   - Если плагин экспортирует `on_data(ptr: i32, len: i32) -> i32`, по умолчанию включается режим `data_mode: "once"`: первый `Read()` клиента (читается не более 16 389 байт) проверяется в памяти WASM **до** `dial` к бэкенду, а после `VerdictAllow` сбрасывается через `DrainTo`, и остаток соединения возвращается на ядерный zero-copy `splice(2)`. `once` — это **подсказка для маршрутизации/мутации первого пакета, а не полноценный фильтр**: клиент может отправить 1 байт и обойти проверку остального payload. Для фильтрации используйте `stream`.
   - При `data_mode: "stream"` через `on_data`/`on_data_ex` проверяется каждый чанк (также `0 allocs/op` за счёт `bufferPool` и scratch-памяти WASM, но без `splice`). `on_data_ex` получает `conn_id` и `dir`, поэтому видит оба направления и может коррелировать чанки в логах; старый `on_data` вызывается только для `client → server`. `conn_id` **не** даёт надёжного состояния между чанками: инстанс и его память выбираются из пула заново на каждый вызов. `route_pools` в `stream` не применяется.
   - Инстанс WASM берётся из пула **только на время CPU-вызова `on_data` (~76 нс)** и никогда не удерживается на время блокирующего `conn.Read`, поэтому медленные клиенты (Slowloris) не могут исчерпать пул WASM-инстансов.
   - **TLS-терминация** (`listeners[].tls`) расшифровывает поток до `on_data`, поэтому плагин видит открытый текст. **TLS passthrough** (`sni_routes`) оставляет поток зашифрованным: плагин увидит байты `ClientHello`/record'ов. На листенере с терминацией `sni_routes` игнорируется.
   - Инспектируется не более первого `Read()` в режиме `once` (фактический предел буфера — 16 389 байт) и не более `32 KiB` на чанк в `stream`. In-place мутация ограничена тем же окном и переписывает только уже прочитанный в буфер префикс.

## 3. Как собрать свой плагин

### Вариант А — Rust (`#![no_std]`, рекомендуемый)
```bash
cd plugins/examples              # workspace со всеми примерами
rustup target add wasm32-unknown-unknown
cargo build --release --target wasm32-unknown-unknown
for p in ipguard http_guard http_body_guard path_router sni_guard protocol_router redis_guard stream_guard; do
  cp "target/wasm32-unknown-unknown/release/$p.wasm" "$p/$p.wasm"
done
```

Один плагин можно собрать так же, из его каталога:
```bash
cd plugins/examples/ipguard
cargo build --release --target wasm32-unknown-unknown
cp target/wasm32-unknown-unknown/release/ipguard.wasm ./ipguard.wasm
```

### Вариант Б — TinyGo
```bash
cd plugins/examples/ipguard/tinygo
tinygo build -o ../ipguard.wasm -target=wasm-unknown -no-debug .
```

## 4. Per-connection state: как устроен ABI v3 (`on_data_state`)

Stateless-плагины (`on_data` / `on_data_ex`) видят каждый TCP-чанк изолированно, потому что
инстансы WASM берутся из `sync.Pool` заново на каждый вызов. Для полноценной работы с
HTTP-телом, разорванными заголовками и keep-alive реализован **host-managed bounded state
(ABI v3, opt-in)**:

- Модуль экспортирует `on_data_state(conn_id, dir, state_ptr, state_len, state_cap, data_ptr, data_len) -> i64`,
  `on_data_ptr() -> i32` (32 KiB) и `on_state_ptr() -> i32` (4 KiB). При инициализации хост
  проверяет, что оба буфера помещаются в линейную память и **не пересекаются**.
- На соединение с ABI v3-плагином в `stream`-режиме хост берёт из `sync.Pool` структуру
  `ConnState` с двумя независимыми 4 KiB буферами (`dir = 0` и `dir = 1`). Мьютексов нет:
  каждое направление принадлежит своей pipe-горутине.
- Перед вызовом хост копирует только `state_len` активных байт в `state_ptr`, вызывает хук,
  читает из старших 32 бит возврата `new_state_len` (`0 <= new_state_len <= 4096`), сохраняет
  обновлённое состояние в `ConnState` и **зануляет** использованный участок `state_ptr` в
  памяти WASM до возврата инстанса в пул (утечка состояния между соединениями исключена).
- Горячий путь без плагина, `once`-режим (`splice(2)`) и плагины ABI v1/v2 не меняются
  (`0 allocs/op`, ~85 нс на `on_data`, ~115 нс на минимальный `on_data_state`).
- Эталонная реализация — `plugins/examples/http_body_guard`.
